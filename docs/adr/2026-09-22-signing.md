# 2026-09-22: Signing protocol and secret rotation

## Context
Legacy signatures authenticate time/body but leave the deduplication header unsigned. Application-only encryption allows ciphertext swapping between endpoints of the same application. Existing receivers must continue working.

## Decision
New endpoints use Standard Webhooks; existing rows keep LEGACY until explicit migration. Sign the server Event ID (stable across delivery generations), timestamp, and raw body. Producer keys can contain delimiters and remain metadata. Preserve legacy key bytes, presenting their base64 representation with whsec_ in standard mode. Test with the specification's independent verifier.

Bind AES-GCM to application, endpoint and monotonically increasing secret version, plus encryption-key version. Keep a versioned prefix so future encryption keys coexist. Deploy compatible readers before the atomic ciphertext migration. Rotation permits two keys for seven days and rejects a third during grace. Audit every display and rotation. Legacy primary signatures retain the old key until expiry, while an additional header carries the new signature.

## Consequences
No forced receiver migration or timing change. Legacy endpoints retain their unsigned-ID limitation until explicitly migrated. Old encryption keys must remain available until all references are migrated. Audit records outlive resource deletion and never contain secrets. Rolling back an old binary after ciphertext migration requires compatible ciphertext restoration.
